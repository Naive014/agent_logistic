# Два почтовых агента для ТЗ

Актуальная структура CSV, временные метки и отдельные логи описаны в [docs/audit.md](docs/audit.md). Готовый файл теперь называется `out_<исходное имя>.xlsx`, например `out_Пример ТЗ.xlsx`.

## Текущая схема

request-agent (PY1 на схеме) за один проход берёт одно непрочитанное письмо [FORECAST_INPUT] с .xlsx из agent_planing@logrocket.ru. Он проверяет и сохраняет исходный файл, создаёт JSON, записывает связь UID и файла в workdir/requests.csv со статусом `prepared`. Почту в Outlook этот агент не отправляет.

result-agent (PY2 на схеме) выполняет за проход один шаг общей очереди. Сначала он ищет пригодный ответ из agent_planing_to_outlook@logrocket.ru и, если находит, дополняет исходный Excel столбцами «Прогноз M1», «Прогноз M2» и «Прогноз M3», затем отправляет его автору через agent_planing@logrocket.ru. Если готового ответа нет, он берёт один старейший JSON со статусом `prepared`, отправляет его через agent_planing_to_outlook@logrocket.ru в Outlook и переводит запись в `sent`. Ожидание ответа асинхронное: в следующих проходах агент продолжает проверку, не блокируя процесс на одном письме.

## Запуск

Нужен Python 3.11+. Из каталога проекта:

Однократный запуск нужного агента из корня проекта:

```powershell
.\run-agent.cmd request-agent
.\run-agent.cmd result-agent
```

Скрипт проверяет наличие `.env`, при необходимости создаёт `.venv`, устанавливает
зависимости и выполняет один проход выбранного агента. При следующих запусках
повторная установка не нужна. Агенты можно вызывать независимо и в разное время.

Диагностические команды можно передать этому же запускателю:

```powershell
.\run-agent.cmd check-mail
.\run-agent.cmd request-agent --continuous
.\run-agent.cmd result-agent --continuous
.\run-agent.cmd run-agents
```

Ручная установка, если она нужна:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
```

Создайте .env по .env.example только на новом компьютере. Не перезаписывайте уже заполненный .env.

Запуск обоих агентов одной командой из каталога проекта:

```powershell
.\.venv\Scripts\shipment-forecast-agent.exe run-agents
```

Команда держит два отдельных процесса в одном окне. Ctrl+C останавливает оба: сначала ожидает завершения текущих операций, затем при необходимости завершает зависший процесс. Если один процесс неожиданно завершился, второй тоже останавливается с сообщением об ошибке. Обычные ошибки почтового соединения обрабатываются внутри агентов с повтором следующего опроса. Не запускайте одновременно общий запуск и отдельные агенты. Это локальная команда, не HTTP endpoint; окно должно оставаться открытым, компьютер — включённым. Автозапуск после перезагрузки не устанавливается.

Либо по отдельности, в двух окнах PowerShell:

```powershell
.\.venv\Scripts\shipment-forecast-agent.exe request-agent --continuous
```

```powershell
.\.venv\Scripts\shipment-forecast-agent.exe result-agent --continuous
```

Без параметров `request-agent` и `result-agent` выполняют ровно один проход и завершаются. Флаг `--continuous` включает повторную проверку каждые POLL_INTERVAL_SECONDS (по умолчанию 30); остановка — Ctrl+C. Старый флаг `--once` оставлен для совместимости, но больше не требуется. `process-inbox` готовит одно входное письмо, а `receive` выполняет один проход второго агента: завершает один ответ либо отправляет один подготовленный JSON.
Автозапуск после перезагрузки не установлен. Один экземпляр каждого агента; оба процесса должны использовать общий WORK_DIR на локальном диске. Блокировки CSV снимаются ОС при завершении процесса.

check-mail проверяет авторизацию без отправки; self-test-mail отправляет тест техническому ящику самому себе.

## Настройки

- MAILBOX_NAME / MAILBOX_PASSWORD — технический ящик agent_planing_to_outlook@logrocket.ru.
- INPUT_MAILBOX_NAME / INPUT_MAILBOX_PASSWORD — ящик входящих ТЗ agent_planing@logrocket.ru.
- INTERNAL_OUTLOOK_EMAIL — smirnovis@sibur.ru.
- N8N_RESPONSE_SENDER — ожидаемый From ответа; пустое значение использует INTERNAL_OUTLOOK_EMAIL.
- RESULT_MAILBOX — устаревшая настройка, новым обработчиком не используется. Получатель результата — исходный sender из CSV.
- INPUT_SUBJECT_PREFIX — [FORECAST_INPUT].
- N8N_REQUEST_SUBJECT_PREFIX — [N8N_FORECAST_REQUEST].
- N8N_RESPONSE_SUBJECT_PREFIX — используется только старым обработчиком; новый result-agent определяет запрос по `mail_id` внутри JSON и не зависит от темы.
- EXCEL_SHEET — лист ТЗ; пустое значение означает активный лист.
- EXCEL_HEADER_ROW — номер строки заголовков, по умолчанию 1.
- FORECAST_START_MONTH и FORECAST_HORIZON_MONTHS больше не используются новым процессом: param_month_m0 берётся из текущего календарного месяца на компьютере агента.
- TRUSTED_REQUESTERS — разрешённые отправители через запятую; пустой список разрешает всех.
- Серверы общие для двух ящиков: imap.beget.com:993, smtp.beget.com:465, TLS.

Пароли находятся только в локальном .env, исключённом из Git. SEND_RESULTS_TO_REQUESTER относится только к старым функциям: новый result-agent всегда возвращает готовый файл исходному автору из CSV через INPUT_MAILBOX_NAME.

## Excel

Перед отправкой запроса проверяется наличие всех 21 заголовков из согласованного шаблона «Пример ТЗ.xlsx». Их порядок, регистр и лишние пробелы не важны, дополнительные столбцы допускаются. Полный список и поведение при ошибке описаны в [docs/input-validation.md](docs/input-validation.md). Значения обязательны только для пункта отгрузки и региона доставки; остальные поля могут быть пустыми.

В `param_month_m0` передаётся текущий календарный месяц компьютера агента (YYYY-MM), независимо от периодов в Excel. Входной контракт допускает ровно одно уникальное направление. Повторяющиеся строки того же направления разрешены; несколько разных направлений в одном файле отклоняются. Любая колонка месяца сохраняется как прочие исходные данные. В ответе ожидается ровно одно значение forecast на пару пункт–регион, даже если ответ содержит дополнительные поля дат.

Результат — копия исходной книги с добавленными справа столбцами «Прогноз M1», «Прогноз M2» и «Прогноз M3» на выбранном листе. Остальные ячейки, обычные стили, формулы и листы сохраняются средствами openpyxl. Если исходный файл уже содержит старый столбец «Прогноз» или любой из трёх новых столбцов, обработчик отказывается их перезаписывать.
Поддерживается .xlsx; макросы и специфические объекты Excel не гарантируются. Для сложного шаблона с объединениями, таблицами, рисунками и защищёнными листами требуется отдельная проверка на реальном файле. Исходник хранится неизменённым.

## UID и CSV

В теме запроса: [N8N_FORECAST_REQUEST] RQ-<32 hex символа>.
Ключ создаётся из адреса входящего ящика, UIDVALIDITY, UID письма, имени и содержимого вложения. Это не голый IMAP UID: он не уникален между ящиками. Несколько Excel в одном письме получают отдельные ключи.

CSV хранит request_id, mailbox, uidvalidity, mail_uid, filename, source_path, sender, status, output_path.
В workdir/jobs/<UID>/ лежат source.xlsx, request.json, response.json, итоговый `out_<исходное имя>.xlsx` и журналы отправок. Файл `workdir/result-mail-handled.json` не даёт повторно разбирать одни и те же старые ответы и засорять лог одинаковыми ошибками.

JSON запроса:

```json
{
  "mail_id": "RQ-0123456789abcdef0123456789abcdef",
  "param_month_m0": "2026-09",
  "shipment_point_name": "Завод",
  "delivery_point_name": "Область"
}
```

Запрос строго соответствует [schemas/shipment_forecast_input.schema.json](schemas/shipment_forecast_input.schema.json): содержит только `mail_id`, `param_month_m0`, `shipment_point_name` и `delivery_point_name`. `request_id`, `ppr_month`, `directions`, `horizon_months` и `periods` не передаются. Месяц фиксируется при создании `request.json`. Подготовленный JSON хранится на диске до отправки вторым агентом; уже принятые SMTP-сервером запросы не пересылаются.

## Ответ

Тема письма может быть произвольной. Отправитель должен совпадать с настройкой. Ровно одно JSON-вложение. JSON обязан содержать `mail_id` с тем же ключом, что был в запросе. Разрешено поле верхнего уровня либо одинаковое `mail_id` внутри строк `data`/`forecasts`. Если в теме всё же указан ключ RQ-… и он расходится с `mail_id`, ответ отклоняется. Result-agent проверяет и прочитанные письма, поэтому открытие ответа в почтовом клиенте не мешает обработке; повторную отправку предотвращает статус запроса и журнал SMTP.

Допускаются:
- одиночный объект с направлением и тремя полями прогноза;
- массив таких объектов;
- объект с `mail_id`, `status: ok`, `data: [объекты]` и необязательным `row_count`;
- совместимый контейнер `forecasts` с названиями направления `shipping_point` и `delivery_region`.

В актуальном ответе n8n обязательны три числовых неотрицательных значения:
`forecast_m1`, `forecast_m2` и `forecast_m3`. Они записываются в одноимённые
столбцы прогноза. Неполный ответ не считается готовым результатом.

Пример:

```json
{
  "mail_id": "RQ-0123456789abcdef0123456789abcdef",
  "status": "ok",
  "row_count": 1,
  "data": [
    {
      "shipment_point_name": "Завод",
      "delivery_point_name": "Область",
      "forecast_m1": 433.18,
      "forecast_m2": 451.72,
      "forecast_m3": 468.09
    }
  ]
}
```

Ответ без mail_id в JSON, в том числе ранее полученный одиночный пример Ильи, автоматически не обрабатывается. Пустой data не является готовым ТЗ. Ошибки [N8N_FORECAST_ERROR] не считаются результатами и не обрабатываются этим агентом.

## Ошибки и повторы

Входное письмо помечается прочитанным после успешной подготовки Excel и JSON; успешный ответ — после отправки результата пользователю. Открытие письма в почтовом клиенте не мешает result-agent, а для входного агента используется выборка непрочитанных сообщений.
Неуспешные письма остаются непрочитанными, ошибка записывается в консоль, остальные письма продолжают обрабатываться.
Записи отправки smtp_accepted предотвращают дубли. Запись submitting после сбоя блокирует повтор до ручной проверки логов: нельзя безусловно пересылать письмо, которое сервер мог принять.
Состояние sent означает приём запроса SMTP-сервером; completed — приём письма с итоговым Excel сервером, не подтверждение доставки адресату.
Повторно пересланное исходное письмо с новым UID считается новым запросом.

## Совместимость и проверка

Старые команды prepare, convert и send сохраняются для старого контракта; не используйте send для нового CSV-процесса, поскольку он не создаёт запись нового реестра. Старые JSON-схемы в contracts относятся к этому прежнему формату.

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Тесты не отправляют реальные письма. Полный цикл с реальным n8n и вашим шаблоном Excel необходимо проверить отдельно. Автоматический push в GitHub и запуск фоновых обработчиков при изменении кода не выполняются.

В CSV внутреннее имя колонки request_id сохранено для совместимости; наружу этот ключ передаётся только как `mail_id`. Формат ключа RQ-… не изменён. Старые отправленные запросы не пересылаются автоматически. После изменения кода перезапустите run-agents; на уже отправленные запросы обработчик должен вернуть тот же ключ в mail_id.
