# Почтовый агент прогнозирования отгрузок

Агент отвечает за участок PC with Python: принимает Excel, отправляет JSON в корпоративную почту, получает JSON от n8n, формирует Excel и возвращает его автору ТЗ. Сам прогноз не рассчитывает. Outlook и The Bat! на рабочем ПК не требуются.

## Два ящика

| Назначение | Настройки | Локальный ящик |
|---|---|---|
| Приём ТЗ и отправка итогового Excel автору | INPUT_MAILBOX_NAME, INPUT_MAILBOX_PASSWORD | agent_planing@logrocket.ru |
| Отправка JSON и получение ответа n8n | MAILBOX_NAME, MAILBOX_PASSWORD | agent_tender@logrocket.ru |

Оба ящика используют общие серверы Beget: IMAP 993 и SMTP 465 с TLS. Альтернативные порты допустимы только с STARTTLS. Пароли хранятся в исключённом из Git файле .env. Не публикуйте этот файл и рабочие данные workdir.

INTERNAL_OUTLOOK_EMAIL — корпоративный получатель запроса. N8N_RESPONSE_SENDER — ожидаемый адрес отправителя ответа; если пуст, используется INTERNAL_OUTLOOK_EMAIL. Это проверка заголовка From, а не криптографическая проверка подлинности.

TRUSTED_REQUESTERS — список разрешённых авторов ТЗ через запятую. Пустой список разрешает любого отправителя; перед постоянной эксплуатацией задайте список.
SEND_RESULTS_TO_REQUESTER=true включает отправку Excel из первого ящика автору ТЗ.
Если обе переменные INPUT_MAILBOX_* пусты, используется один ящик; заполнение только одной — ошибка.

## Установка и команды

Команды выполняются из каталога проекта, где лежит .env:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e ".[dev]"
pytest -q
shipment-forecast-agent --help
```

Скопируйте .env.example в .env только при первоначальной установке; существующий файл с реквизитами не перезаписывайте.

| Команда | Действие |
|---|---|
| check-mail | Авторизация IMAP/SMTP двух ящиков, без отправки |
| self-test-mail | Реальная отправка письма техническому ящику самому себе и чтение JSON |
| process-inbox | Читает ТЗ и реально отправляет JSON в корпоративную почту |
| receive | Читает ответы и при включённой настройке реально отправляет Excel автору |
| send input.xlsx | Разовая ручная отправка запроса; каждый вызов создаёт новый request_id |
| prepare input.xlsx request.json --reply-to address@example.com | Локальное преобразование без почты |
| convert response.json result.xlsx | Локальное преобразование ответа в Excel |

Команды однократные. Фоновое расписание не установлено. Запускайте один экземпляр обработчика за раз.
SMTP accepted означает только приём сервером Beget, не доставку адресату и не выполнение n8n.

## Входное письмо

Тема начинается с [FORECAST_INPUT], вложение имеет формат .xlsx.
Обрабатываются только непрочитанные письма в INBOX. Не открывайте их в другом клиенте до обработки: прочитанные письма агент не выбирает.
Первая строка Excel — заголовки «Пункт отгрузки» и «Регион доставки». Также поддерживаются «Наименование пункта отгрузки», «Наименование региона доставки», shipping_point и delivery_region.
Пустые строки пропускаются, неполные направления отклоняются. Дубли пункт–регион удаляются без учёта регистра. Остальные заполненные колонки передаются в attributes.
Имя вложения заменяется безопасным локальным именем.

## Контракт JSON

Тема запроса: [FORECAST_REQUEST] <request_id>. Вложение: forecast_request.json.

```json
{
  "schema_version": "1.0",
  "request_id": "85f60ba1-01be-44b9-b079-2b2f3c42ccb6",
  "created_at": "2026-09-21T07:00:00Z",
  "reply_to": "agent_tender@logrocket.ru",
  "directions": [
    {
      "direction_id": "DIR-0001",
      "shipping_point": "Малино",
      "delivery_region": "Смоленская область",
      "attributes": {}
    }
  ]
}
```

В отправляемом JSON и почтовом Reply-To указан технический ящик. В локальном forecast_request.json поле reply_to хранит автора ТЗ для возврата Excel — локальная и отправляемая копии намеренно отличаются.

n8n должен прислать письмо техническому ящику с темой [FORECAST_RESPONSE] <request_id> и JSON-вложением:

```json
{
  "schema_version": "1.0",
  "request_id": "85f60ba1-01be-44b9-b079-2b2f3c42ccb6",
  "generated_at": "2026-09-21T07:05:00Z",
  "forecasts": [
    {
      "direction_id": "DIR-0001",
      "shipping_point": "Малино",
      "delivery_region": "Смоленская область",
      "period": "2026-10-01",
      "forecast": 100,
      "attributes": {}
    }
  ]
}
```

Ответ должен покрывать все запрошенные направления без посторонних. Дубли direction_id + period запрещены. Число прогнозных месяцев пока не фиксируется. Дополнительные атрибуты выводятся отдельными колонками Excel.
Этот контракт ещё нужно согласовать с реальным n8n: исходный пример с ppr_date, ppr_value и forecast не эквивалентен данной схеме.

## Состояние и повторы

workdir/requests/<request_id> хранит запрос и журнал его отправки; workdir/responses/<request_id> — ответ, Excel и журнал отправки результата.
Для входного письма request_id детерминирован по ящику, UIDVALIDITY, UID, имени и содержимому вложения. Повторная обработка того же вложения не отправляет запрос снова.
Повторный ответ с тем же request_id не пересылает уже отправленный Excel.

Журнал submission.json:
- submitting — отправка начата, исход ещё не подтверждён;
- smtp_accepted — SMTP подтвердил приём.

Если соединение оборвалось или процесс завершился после начала отправки, автоматического повтора нет: возможна уже состоявшаяся отправка. Проверьте серверные логи. Только после подтверждения отсутствия отправки можно убрать соответствующий submission.json и повторить команду. Для принятого сервером письма статус восстанавливается только после проверки. Слепое удаление журнала создаёт риск дублей.
Старые отправки до введения журнала автоматически не распознаются; перед первым запуском убедитесь, что ранее обработанные письма помечены прочитанными.
Повторно присланная копия письма с новым UID считается новым ТЗ.

Ошибочные и неизвестные ответы остаются непрочитанными, причины записываются в журнал приложения. После успешной обработки письмо помечается прочитанным.
Если отправка результата выключена, создаётся только локальный Excel; последующее включение флага само по себе не отправляет ранее обработанные результаты.

## Ограничения перед постоянной эксплуатацией

Нужно согласовать схему и отправителя n8n, шаблон Excel, атрибуты и горизонты прогнозирования, затем проверить реальный полный цикл.
Локальные тесты подменяют почтовые серверы и не доказывают доставку. Контроль сроков ожидания ответа, перемещение ошибочных писем, ограничения размера вложений и запуск по расписанию пока не реализованы.
